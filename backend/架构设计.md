# Workstudio 新版后端架构设计

## 1. 目标与范围

- **目标**：在 `backend/` 下实现基于 **FastAPI** 的 **RESTful HTTP API**，对下列两套存储中**同一套三张业务表**分别提供 **增删改查**（路由级区分数据源），供采集层、内部工具或后续前端调用。
  - **远端**：MySQL（与生产/准生产库一致）。
  - **本地**：SQLite 单文件 [`database/stock.sqlite`](../database/stock.sqlite)（路径可由配置覆盖，默认相对仓库根目录）。
- **数据源**：三张表的**名称、主键与字段语义**均以 [`database/远端数据库字段说明.md`](../database/远端数据库字段说明.md) 为准；本地 SQLite **与远端对齐同一逻辑模型**（列名一致，便于同一套 Pydantic / Repository 接口）。本服务不维护「源接口字段 → 库字段」映射，该映射由采集层负责。
- **与现有 `stock.sqlite` 的关系**：当前文件内可能仍含有 `v1/backend` 使用的调度/流水表（如 `runs`、`clist_quotes` 等），与三张标准化业务表**共存**即可。若库中尚未建 `stock_basic_info` / `stock_daily` / `stock_individual_fund_flow`，需按 `远端数据库字段说明` 在 SQLite 侧执行等价 **DDL**（类型按 SQLite 惯用映射：`DATE`/`DATETIME` 可用 `TEXT` ISO8601 或 `NUMERIC`，由 SQLAlchemy 统一处理）。
- **旧版参考**：`v1/backend` 为基于 `http.server` 的本地服务 + 本地 SQLite 与 `pymysql` 写远端，仅作行为与配置参考，**不继承其目录与路由**。

## 2. 技术选型

| 层级 | 选型 | 说明 |
|------|------|------|
| Web 框架 | FastAPI | 异步可选、自动 OpenAPI、Pydantic 校验 |
| 数据访问 | SQLAlchemy 2.x | **远端**：`pymysql` / `mysqlclient`；**本地**：内置 `sqlite3` 驱动（连接串 `sqlite:///...`） |
| 配置 | Pydantic Settings + `.env` | MySQL 与 SQLite 路径、日志级别等与部署环境解耦 |
| API 文档 | OpenAPI 3（`/docs`、`/redoc`） | 与实现同源，减少手工维护 |

**连接配置（建议）**

- 远端：`MYSQL_HOST`、`MYSQL_PORT`、`MYSQL_USER`、`MYSQL_PASSWORD`、`MYSQL_DB`（可与 `v1/backend` 对齐）。
- 本地：`SQLITE_PATH` 或 `DATABASE_URL_SQLITE`，默认指向仓库下 `database/stock.sqlite`（Windows/Linux 注意路径与权限；服务启动时可 `check_same_thread=False` 等多线程约定按 SQLAlchemy 文档配置）。

## 3. 分层与职责

```
HTTP (FastAPI Router)
    → Schema（请求/响应 Pydantic 模型，与 OpenAPI 一致）
    → Service（业务规则：批量写入策略、幂等 upsert、日期范围校验等）
    → Repository / CRUD（按表封装 SQL，事务边界）
    → SQLAlchemy Model（仅映射已存在的表，不负责迁移）
```

- **Router**：只做路由、依赖注入、HTTP 状态码与错误体转换。
- **Schema**：入参校验、输出序列化；可区分「创建」「部分更新」模型（`POST` 全量 / `PATCH` 可选字段）。
- **Service**：跨行跨表规则可后移；首版可薄封装，与 Repository 合并。
- **Repository**：三张表各自独立模块；**构造函数或方法入参接受 `Session`**，同一套实现可对 **MySQL Session** 与 **SQLite Session** 复用（仅方言差异由 ORM/DDL 消化）。
- **双数据源**：通过 FastAPI `Depends` 注入 `get_db_mysql` / `get_db_sqlite`（或命名 `get_db_remote` / `get_db_local`），**不在 Repository 内写死引擎**。

**错误约定**（建议）：校验失败 `422`；资源不存在 `404`；冲突（如违反唯一约束）`409`；服务端/数据库错误 `500`，body 使用统一 JSON（如 `{"detail": "..."}` 或与内部规范一致）。

### 4.1 Windows 生产环境启动与停止（与 `v1/backend` 对齐）

新版在 `backend/` 下提供与旧版 **`v1/backend/start_prod_win.ps1`、`v1/backend/stop_prod_win.ps1`** 同构的脚本，便于本机长期挂接服务：后台运行、**PID 文件**、**标准输出/错误分文件**、启动前检测「已在运行则拒绝二次启动」。差异仅在于进程入口：旧版为 `python app.py serve`，新版为 **`python -m uvicorn app.main:app`**（FastAPI 应用位于 `app/main.py`）。

| 项 | 约定 |
|----|------|
| **启动脚本** | `backend/run_prod_win.ps1` |
| **停止脚本** | `backend/stop_prod_win.ps1` |
| **PID 文件** | `backend/backend_prod.pid`（仅一行进程号；与 v1 文件名相同但路径不同，互不冲突） |
| **日志目录** | `backend/logs/`，按次启动生成带时间戳的文件，如 `backend_yyyyMMdd_HHmmss.out.log` / `.err.log` |
| **监听地址** | 环境变量 **`BACKEND_HOST`**、**`BACKEND_PORT`**。未设置时由脚本尝试从**仓库根目录** `.env` 注入（已存在于当前进程环境的键不覆盖）；再默认 **`127.0.0.1:8000`**（与 v1 默认 `LOCAL_PORT=17890` 区分，避免同时跑两套时误占端口）。 |
| **控制台语言** | 启动/停止脚本向终端输出的**提示与错误信息使用英文**（日志文件内容不受影响）。 |
| **前置条件** | 需已安装 **`uvicorn`**（随后端依赖安装）；存在 `app/main.py`；本机 PATH 可执行 `python`。 |
| **子进程环境** | 与 v1 类似，子进程继承当前环境；若未设置 **`LOG_LEVEL`**，脚本可默认为 **`WARNING`** 以减少控制台噪声（应用内日志策略以代码为准）。 |

**用法示例**（在 `backend/` 目录执行）：

```text
powershell -NoProfile -ExecutionPolicy Bypass -File .\run_prod_win.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\stop_prod_win.ps1
```

**仓库忽略**：`backend_prod.pid` 不应提交版本库；根目录 `.gitignore` 已包含 `backend/backend_prod.pid`。

---

- **版本前缀**：对外路径统一 `/api/v1/...`，便于日后 breaking change。
- **数据源前缀**：三张表的业务路径在 **本地** 与 **远端** 各有一套，仅在第一段路径上区分（推荐）：
  - **SQLite（本地文件）**：`/api/v1/local/...`
  - **MySQL（远端）**：`/api/v1/mysql/...`（若部署上「远端」不一定是 MySQL，可改名为 `/api/v1/remote/...`，与配置命名一致即可）。
- **实现复用**：`schemas/`、`models/`、`repositories/` **只保留一套**；`api/v1/local/*.py` 与 `api/v1/mysql/*.py` 中路由处理函数可委派同一套 Repository，仅 `Depends` 注入的 `Session` 来源不同。也可使用 **路由工厂** `def build_router(get_db: Callable)` 减少重复文件（二选一，团队在「显式双文件」与「DRY」间权衡）。
- **健康检查**：`GET /health` 或 `GET /api/v1/health`（二选一，全文档与代码保持一致即可）；可返回 `{"sqlite": "ok|fail", "mysql": "ok|fail"}` 分别 `SELECT 1`。

## 5. 资源与主键映射（CRUD 设计基础）

| 表名 | 业务含义 | 主键 | URL 中主键表达 |
|------|----------|------|----------------|
| `stock_basic_info` | 证券静态信息 | `(exchange, stock_code)` | 路径两段：`{exchange}`, `{stock_code}` |
| `stock_daily` | A 股日线行情 | `(stock_code, trade_date)` | 路径两段：`{stock_code}`, `{trade_date}`（日期 `YYYY-MM-DD`） |
| `stock_individual_fund_flow` | 个股资金流 | `(stock_code, trade_date)` | 同上 |

列表接口建议统一：**分页** `skip`/`limit` 或 `page`/`page_size`；**筛选**用 query（如 `exchange`、`board`、`stock_code`、`trade_date_from`、`trade_date_to`）。排序默认与索引友好字段一致（如按 `trade_date` 降序）。

## 6. RESTful API 说明

以下资源路径均落在 **`/api/v1/local`**（SQLite：`database/stock.sqlite`）或 **`/api/v1/mysql`**（远端 MySQL）之下，**相对路径相同**；媒体类型 `application/json`。字段名与数据库列名保持一致（蛇形命名），便于与 [`database/远端数据库字段说明.md`](../database/远端数据库字段说明.md) 对照。

记 **`<store>`** 为 `local` 或 `mysql`，则完整前缀为 **`/api/v1/<store>`**。

### 6.1 证券静态信息 `stock_basic_info`

资源集合路径：`/<store>/stock-basic-infos`（或 `/stock-basic-info`，全文统一即可）。

| 方法 | 路径 | 说明 |
|------|------|------|
| `GET` | `/<store>/stock-basic-infos` | 列表；支持 query：`exchange`、`board`、`security_type`、`stock_code` 精确、`skip`、`limit` |
| `POST` | `/<store>/stock-basic-infos` | 创建一条；体为完整或必填字段子集；违反主键/唯一约束返回 `409` |
| `GET` | `/<store>/stock-basic-infos/{exchange}/{stock_code}` | 单条查询 |
| `PUT` | `/<store>/stock-basic-infos/{exchange}/{stock_code}` | 全量替换（除主键外字段均以 body 为准） |
| `PATCH` | `/<store>/stock-basic-infos/{exchange}/{stock_code}` | 部分更新（仅提交需变更字段） |
| `DELETE` | `/<store>/stock-basic-infos/{exchange}/{stock_code}` | 删除一行（若生产策略禁止物理删除，可改为 `501` 或软删字段——当前表结构无软删列，需与业务确认） |

**响应体**：单条为表中各列 + `created_at`/`updated_at`；列表可包装为 `{"items": [...], "total": n}`（`total` 需 count 查询时再实现）。

| 方法 | 路径 | 说明 |

**注意**：`stock_name` 等为采集时快照字段，更新策略与采集侧对齐。

### 6.4 批量与幂等（扩展，可选）

采集写入多为批量 upsert。可在首版之后增加：

- **MySQL**：`POST /api/v1/mysql/stock-dailies/...` 的 bulk 端点，body 为数组 + `ON DUPLICATE KEY UPDATE`，与 `v1/backend` 中远端写入语义对齐。
- **SQLite**：`POST /api/v1/local/stock-dailies/...` 可使用 `INSERT OR REPLACE` / `ON CONFLICT` upsert（方言与 MySQL 不同，实现放在 Repository 或专用 `bulk_upsert` 方法中）。

此类端点需在 OpenAPI 中单独标明**非标准 REST**，避免与单资源语义混淆。

---

### 6.5 本地 → 远端按交易日同步（动作型接口）

将本地 SQLite（`database/stock.sqlite`）中 **标准化表** `stock_daily` 或 `stock_individual_fund_flow` 在 **某一交易日** 的全量行，**读取后批量 upsert 到远端 MySQL 对应表**。语义是「**以本地该日数据为准覆盖/写入远端**」，与 `v1/backend` 中按 run 从 staging 表写远端的链路不同，但写入远端时可复用相同的 **INSERT … ON DUPLICATE KEY UPDATE** 策略。

**共性约定**

- **前缀**：`/api/v1/sync`（与 `/local`、`/mysql` 并列，表示跨存储动作）。
- **方法**：`POST`（有副作用；重复调用同一 `trade_date` 应 **幂等**：结果仍为该日远端与本地一致）。
- **路径参数**：`trade_date`，格式 `YYYY-MM-DD`，与库中 `DATE` 一致。
- **请求体**：可无；若有扩展字段（如 `dry_run: true`）可在后续版本增加。
- **成功响应**：`200`，JSON 建议包含至少：`trade_date`、`rows_read`（本地读取行数）、`rows_affected` 或拆分为 `inserted` / `updated`（若 ORM/驱动能区分；不能则只给 `rows_upserted`）。
- **错误**：`422` 日期格式非法；`503` / `502` 远端 MySQL 不可用或写入失败；`500` 其他服务端错误。若本地该日 **无任何行**，仍返回 `200`，`rows_read: 0`，`rows_upserted: 0`（便于脚本重试与对账）。

**接口 1：同步日线 `stock_daily`**

| 方法 | 路径 | 说明 |
|------|------|------|
| `POST` | `/api/v1/sync/stock-daily/{trade_date}` | 将本地 `stock_daily` 中 `trade_date = {trade_date}` 的所有行同步到远端 `stock_daily` |

**接口 2：同步个股资金流 `stock_individual_fund_flow`**

| 方法 | 路径 | 说明 |
|------|------|------|
| `POST` | `/api/v1/sync/stock-individual-fund-flow/{trade_date}` | 将本地 `stock_individual_fund_flow` 中 `trade_date = {trade_date}` 的所有行同步到远端同名表 |

**实现要点**

- **事务**：建议「读本地 → 写远端」中，远端使用**单事务批量提交**（或合理分块），避免半写成功；失败则回滚远端事务并返回错误。
- **性能**：单日行数较大时分批 upsert，控制单次绑定参数与内存。
- **权限**：与写远端 CRUD 相同，建议仅内网或鉴权后开放。
- **与 CRUD 的关系**：不改变第 6.1–6.3 节单表 CRUD 语义；同步是**显式**触发的跨库动作。

## 7. 与旧版的关系与迁移注意

- **旧版** `v1/backend`：控制面、本地 `stock.sqlite`（`runs`、`clist_quotes` 等）、`http.server` 等与「双存储 REST CRUD」目标不同；新版 **聚焦标准化三张表** 在 **本地 SQLite 与远端 MySQL** 上的同一套 API 形态。
- **写入策略**：若生产以采集为主，API 的 `POST/PUT` 可能仅用于补数或运维；删除需权限与审计，架构上预留中间件或 API Key / JWT（本设计不强制，由部署决定）。
- **字符集**：MySQL 与表设计一致，使用 `utf8mb4`；SQLite 文本为 UTF-8；路径中的 `exchange`、`stock_code` 需 URL 编码。
- **双写/同步**：普通 CRUD **不**做隐式双写。跨库对齐通过 **显式接口** 完成（见 **6.5 本地 → 远端按交易日同步**）；若还需「远端拉回本地」等能力，可另增对称端点，避免歧义。

## 8. 后续可补充项

- 统一日志格式（request id、耗时、SQL 慢查询阈值）。

## 9. 浏览器扩展（Quant Pilot）与采集链路

本节说明 **采集侧（Chrome 扩展）** 与本文前述 API 的协作边界；扩展自身分层与 Debugger / 分页等细节见 [`browser-extension/quant-pilot/架构设计.md`](../browser-extension/quant-pilot/架构设计.md)。**扩展与本服务之间只保留这一套 HTTP 契约**，不再依赖其它本机采集后端。

### 9.1 职责划分

| 组件 | 职责 |
|------|------|
| **扩展** | 在东方财富列表页取证 `qt/clist/get` 等响应、分页自动化、将 **源 JSON 映射为与库一致的字段语义** 后提交本机服务；可选展示任务状态与健康检查结果。 |
| **本服务 `backend/`** | 对三张标准化表提供 **local / mysql** CRUD 与 **按交易日的 sync**（§6.5）；**不**内置东方财富接口字段 → 表列的映射逻辑。 |

### 9.2 集成方式

1. 扩展将采集结果写入 **本地 SQLite**：调用 **`POST /api/v1/local/...`**（单条或后续 **bulk/upsert** 端点，见 §6.4）。
2. 需要对齐远端 MySQL 时，由运维/脚本/控制台显式调用 **`POST /api/v1/sync/stock-daily/{trade_date}`** 或 **`POST /api/v1/sync/stock-individual-fund-flow/{trade_date}`**，保持「隐式无双写」原则（§7）。
3. 健康与编排：扩展通过 **`GET /health`** 感知 `sqlite` / `mysql` 可用性。若需要 **任务 ID、分页批次、仪表盘聚合** 等与 §5–§6 资源模型正交的元数据，应在 **同一 `backend/` 进程** 内增补 **采集编排** 路由与存储；扩展 **只**与此服务的基址通信（默认主机与端口见 **4.1**）。
